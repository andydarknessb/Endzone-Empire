# Acceptance criteria in agent briefs

A criterion is a **result** the assigned actor can observe from inside its own sandbox, worded so a reader can tell red from green. The tell for a weak one: it names a **thing** (a suite, a job, a live session) where a result belongs. Each thing a criterion names has passed three lookups before the brief is posted:

1. **Exists.** The command, script, suite or fixture is in the tree today: `git grep` it, or read the `scripts` block of `package.json`. A rhetorical reference in the prose ("even axe would miss this") stays prose. #354's checklist turned it into "the axe suite still passes", and no axe suite has ever been in this repo; the IC spent time hunting for it. For a test command, existence means the repo configures the runner it names, not merely that the binary sits in `node_modules/.bin`: a runner's transform and config can live inside another package. `npx jest <path>` passes a naive check because `node_modules/.bin/jest` is present, pulled in by `react-scripts`, and then fails everywhere with a transform error, because this repo carries no `babel.config.*`, `.babelrc*` or `jest.config.*` of its own; run from the repo root it also matches every stale copy of the named file under `.claude/worktrees/` (see `docs/agents/stale-worktrees.md`'s related note on worktree test discovery), so even a working transform would run more than the one file named. #709 and #706 both shipped `npx jest <path>` as an acceptance criterion, and both assignees spent time establishing that a criterion they had been handed was impossible. The working forms are `npm test -- <path>` (through `react-scripts test`, which is what CI runs), `CI=true npx react-scripts test --env=jsdom --watchAll=false <path>` for a non-watch single-file run, and `node --test <file>` for the repo's `node --test` suites, which span `scripts/` and `server/test`, not only `scripts/ci`.
2. **Producible.** The actor can make it from a branch and a PR. A required-check setting, a merged workflow's first green run on `integration`, an applied migration and a Render env var are the maintainer's actions, so the criterion stops at what the PR carries: the job definition, the migration file, the `Carve-out:` heading naming the post-merge action. #247 asked an IC for a job "required for merge on the same footing as the existing unit job".
3. **Observable.** The actor can see the result without a production side effect. The dev database is production, so a live session is not an IC observation; the observable stand-ins are a unit test rendering from the new shape and a `tests/e2e` spec on the mocked origin (the specs route `**/api/**` themselves). #344 asked for "a live Draft with two browsers, recorded in the PR body".

Write the criterion from what the lookups return: a command and its exit status, an assertion and the input that turns it red, a line the PR body must carry. Where the real check needs a human (a screen-reader pass, a two-browser session against production), the brief says so and the ticket is `ready-for-human`, or the human half becomes its own child issue.

| Names a thing | Names a result |
|---|---|
| The axe suite still passes. | `npm test -- src/theme/tokens.contrast.test.js` is green, and lowering the hero tint's alpha in the test-only value turns it red. |
| The job is required for merge. | The PR adds the job to `ci.yml` on the unit job's triggers; renaming one guard script in a throwaway commit turns it red, run linked in the PR body. Making it required is the maintainer's step, named under `Carve-out:`. |
| A live Draft with two browsers shows picks attributed by Team name. | A `tests/e2e` spec on the mocked origin renders a pick, a presence entry and a chat line from the post-removal payload shape, each attributed by Team name; the builder key-set tests are green. |

**Content vs. behaviour.** A criterion phrased over file contents is only safe when the string cannot legitimately appear in a comment, a test, or documentation. Otherwise phrase it over rendered output, or scope the paths explicitly and say which. A guard that must embody the thing it forbids (an absence assertion, a lint rule quoting the banned pattern, a fixture holding invalid input, or the document that explains the check) will break a naive content check, since explaining or forbidding a convention means writing an example of it; exclude those paths deliberately rather than discovering the collision later. Where a content check is right, state it in the form that survives: `-F` when the pattern contains regex metacharacters, and a positive control proving a pathspec exclusion did not exclude everything. #402's AC3 (`grep "League Pick'em" src/components/public` returns nothing) was broken by the test asserting that heading's absence, which is work that satisfied the criterion's intent; the corrected form is `git grep -nF "League Pick'em" src/components/public ':!*.test.*'`, with `git grep -nF "Pick'em" src/components/public ':!*.test.*'` as the positive control, returning two component files.

**Which tests a mutation binds.** A red-tell criterion that names one mutation for a set of tests must say which tests in that set it binds. A presence assertion and an absence assertion are not sensitive to the same mutation: an absence reached by an earlier guard clause never reads the value the mutation changes, so it cannot go red under that mutation, and a criterion phrased over the whole set never moves together. #825's AC2 said "every new and restored test" turns red under `viewerTurn: null`; three cases assert a rendered `Next pick <label>` or `remainingPicks` and do go red, but the fourth asserts a spectator sees neither, and `rosterViewFor`'s `myTeam` early return (`DraftBoard.jsx:88`) fires before `viewerTurn` is ever read, so that case cannot go red under the named mutation. The corrected form names the three presence cases and states the absence case's exemption separately.

**A literal a criterion hands to an artifact.** When a criterion tells the actor to put an exact string into a PR body, a commit message or a file, an obedient IC reproduces it exactly, wrapper and all, so whatever markup the brief sets the literal in becomes part of the artifact. Where the artifact is machine-read, the wrapper can change what the machine sees, and nothing goes red: the check the brief cares about is a different check, CI is green, and the wrong string ships. So the brief writes the literal the way the artifact must carry it, says where in the artifact it goes, and names a command that reads the string back the way the machine will. The closing keyword is the worked failure, because setting a literal in code style is the natural way to write one in prose and it is exactly the wrapper that bites. #904's criterion 6 wrapped `Closes #N` in backticks as ordinary emphasis; PR #926 copied it verbatim and would have merged with #904 left open, which is the finding recorded in #930. The #330 auto-closer, `scripts/ci/close-merged-issues.js`, runs `stripCode` over the PR body first, deleting fenced blocks and inline code spans, and only then scans the remaining text for the keyword, so a backticked `Closes #N` is gone before the scan ever runs. The repo cannot fall back on GitHub's own closing link, because the fleet opens PRs against `integration`, which is not the repo's default branch, and GitHub populates its native closing linkage only for the default branch, so the #330 workflow is the only closer. Scope the rule to what actually bites: the trap fires only when the body carries the backticked form and no plain form. A body carrying both still closes, because `stripCode` removes the wrapped copy and the scan finds the unwrapped one; #873 carried both and closed #865 normally. Check a body before trusting it with `node -e "const {parseClosingReferences}=require('./scripts/ci/close-merged-issues.js');const fs=require('fs');console.log(JSON.stringify(parseClosingReferences(fs.readFileSync(process.argv[1],'utf8'),{owner:'andydarknessb',repo:'Endzone-Empire'})))" <path-to-body-file>`, run from the repo root: a body the workflow will act on prints `{"issues":[930],"foreignRefs":[]}`, and a backticked-only body prints `{"issues":[],"foreignRefs":[]}`. Its positive control is the same body with the backticks removed; if both forms print the same set, the command is not reading what you think it is and the check proves nothing. So a brief that needs the string in an artifact writes the closing keyword unbackticked and on its own line, and a brief that only quotes the convention in its own prose tells the IC to verify the finished body with this command rather than to copy the quoted form.

A criterion that turns out unmeetable as written is recorded on the PR as unmet, with the reason (PR #374 did this for #354's AC6), and the brief is corrected. A tick on it would tell the next reader that a check ran which never existed. The record states what was tried to make the criterion meetable, not only why it is not met: "unmeetable as written" is unfalsifiable by a reader, while "unmeetable, and here is the reformulation I attempted and why it fails" is checkable, and writing that sentence is what surfaces a reformulation that works. #402 recorded a tolerated exception for its AC3 without trying one; the pathspec exclusion above was available and would have satisfied the criterion at filing.
